  The joint is the product of each variable's local conditional probability given its parents:
  \[
    \mathbb{P}(\text{Rain} = r, \text{Sprinkler} = s, \text{WetGrass} = w)
      = p(r)\, p(s)\, p(w \mid r, s) .
  \]
  % ### END CODE HERE ###
\end{answer}

% <SCPD_SUBMISSION_TAG>_1d
\begin{answer}
  % ### START CODE HERE ###
  The grass is wet with probability 0.9 when it rained and the sprinklers were on, so it stays dry
  with probability $1 - 0.9 = 0.1$:
  \[
    \begin{aligned}
      \mathbb{P}(\text{Rain} = 1, \text{Sprinkler} = 1, \text{WetGrass} = 0)
        &= p(\text{Rain} = 1)\, p(\text{Sprinkler} = 1)\, p(\text{WetGrass} = 0 \mid \text{Rain} = 1, \text{Sprinkler} = 1) \\
        &= 0.2 \times 0.5 \times 0.1 = 0.01 .
    \end{aligned}
  \]
  % ### END CODE HERE ###
\end{answer}

\begin{answer}
  % ### START CODE HERE ###
  Claude Code is more likely to replace entry-level work and augment experienced developers than to
  replace developers outright. Stanford's \textit{Canaries in the Coal Mine} study finds employment
  for 22 to 25 year olds in AI-exposed jobs, software development included, is now 19\% below where
  it should be while experienced workers show no gap, and the losses are concentrated in jobs where AI
  automates rather than assists, which fits Claude Code being used mostly for automation
  (\href{https://digitaleconomy.stanford.edu/news/canariesaug26/}{Stanford Digital Economy Lab}). For
  workers the risk is that if companies stop hiring juniors, there is no route to becoming a senior,
  so the pipeline of experienced developers dries up. For employers the risk is code that nobody
  fully understands, since code can pass its tests while still being subtly wrong, which I ran into
  several times in this course. Layoffs blamed on AI are real, but those are companies' stated
  reasons, so it is hard to tell how many jobs were actually replaced.
  % ### END CODE HERE ###
\end{answer}

  Instead of giving everyone full automation up front, companies could scale how much Claude Code

6.a
\normalsize

% <SCPD_SUBMISSION_TAG>_6a
\begin{answer}
  % ### START CODE HERE ###
  Claude Code is Anthropic's agentic coding tool. It runs in the terminal or an IDE, reads a codebase,
  edits files, runs commands and makes commits and pull requests, working towards a goal on its own
  and asking for approval according to its permission mode. Its strengths showed in my own use: it
  added a feature and unit tests to an existing investment backtester, built an application from
  scratch, and worked as a tutor through this course. Anthropic markets it mostly through developer
  channels rather than hype, and publishes a system card for each model, a plain-language usage
  policy and regular threat intelligence reports. Its weaknesses are mostly about what users cannot
  see or control. The training default for consumer accounts is never stated, the Claude Code data
  page is hard to find, and anything sent through \texttt{/feedback} is kept for five years. Individual
  users get no copyright indemnity while businesses do, and support is private and asynchronous with
  no public record of what was reported or fixed. Its fairness testing covers only the chat model,
  with multilingual results reported as a single average. And because it is used mostly for
  automation, it puts entry-level developers at the most risk, while its code can pass tests and
  still be subtly wrong.

  On privacy and accountability, I would state the training default plainly and show the current
  setting, and what it means for retention, the first time Claude Code is launched. I would add a
  per-session view showing whether each session was kept for training and when it will be deleted,
  and tie the retention of \texttt{/feedback} reports to the user's training setting rather than a
  flat five years. I would also make reported issues public, with what Anthropic did about each one
  and a way for users to vote on what gets fixed first, so users have real influence over the
  product.

  On fairness and jobs, I would publish Claude Code's own task success and error rates broken down by
  prompt language and plan tier, so performance gaps can actually be seen and tracked. For junior
  developers, I would offer a mode that starts with low automation and high oversight, explaining
  rather than writing finished code and asking before each action, and gradually hands over more
  automation as the developer gains experience. Finally, I would extend copyright protection to
  individual users, or at least flag outputs that closely match known licensed code, so the risk is
  not left entirely on the people least able to carry it.
  % ### END CODE HERE ###
\end{answer}

  Right now Anthropic decides how Claude Code changes, with its engineers building it and its
  executives deciding what ships, and the only outside groups with real power are courts and paying
  businesses: in the music publishers' case Anthropic agreed to keep its copyright guardrails in place
  while the case continues, and the commercial terms give businesses protections that individual
  users do not get. Individual users can report problems through \texttt{/bug} and the GitHub
  tracker, but that path is private and slow, with over 5,000 open issues, so in practice they have
  almost no say. I think users should have real influence too, since they are the ones whose code,
  data and jobs are affected, and they are the first to see its problems. One way to shift that would
  be a public record of reported issues and what Anthropic did about them, with users able to vote on
  what gets fixed first, so their feedback has visible weight instead of disappearing into a private
  queue.
