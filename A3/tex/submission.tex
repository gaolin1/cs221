\begin{answer}
  % ### START CODE HERE ###
  % Kept for reference, not rendered. How I got here:
  %  - Cost((x, y), a) is priced on the state being LEFT, and depends only on
  %    x: 1 + x for x >= 0, and 1 for x < 0. Direction does not matter, so a
  %    north step from x = 2 costs 3, not 1.
  %  - each action moves one coordinate by one, so every step is priced
  %    separately; the formula is applied per step, never once per leg
  %  - checked by hand: (2, 1) north-first costs 1 + 1 + 2 = 4, while
  %    east-first costs 1 + 2 + 3 = 6; (3, 0) costs 1 + 2 + 3 = 6
  %  - guesses that failed a hand check: 1 + m, 1 + m + n, 2n + m, 2m + n
  %  - closed form of 1 + 2 + ... + m by writing the series forwards and
  %    backwards: m columns each summing to m + 1, two copies of the series,
  %    so the sum is m(m + 1)/2. Works for odd m, where pairing leaves a middle
  %    term.
  The minimum cost of reaching $(m,n)$ from $(0,0)$ is
  \[
    \frac{m(m+1)}{2} + n .
  \]
  The cost only depends on the $x$ being left, so take all $n$ north steps while still at $x = 0$,
  where each costs 1 and they total $n$, then the $m$ east steps leave from $x = 0, 1, \dots, m-1$
  in turn and cost $1, 2, \dots, m$; writing that series forwards and backwards pairs it into $m$
  columns of $m+1$, so it sums to $m(m+1)/2$. One path achieving the minimum is to take all $n$
  steps north from the origin first and then all $m$ steps east, and it is the only one, since any
  north step taken after moving east costs more than 1 because it leaves from $x > 0$, and a detour
  into negative $x$ adds at least one step west and one step back east, each costing at least 1,
  without making any other step cheaper.
  % ### END CODE HERE ###
\end{answer}

\begin{answer}
  % ### START CODE HERE ###
  % Kept for reference, not rendered. What I had to get straight:
  %  - "pop" means taking a state OUT of the frontier to process it. Popping a
  %    state makes its cost final; it does not stop the search. UCS stops only
  %    when the state it pops is the goal.
  %  - the frontier is a priority queue deciding who gets processed next,
  %    ordered by past cost. Expanding a state pushes all four neighbours, but
  %    UCS always processes the cheapest known state next, so it grows in rings
  %    of increasing cost rather than racing off in every direction.
  %  - ties are not random here: util.PriorityQueue stores (priority, state)
  %    tuples, so equal priorities are broken by comparing the states, lower x
  %    first then lower y: (-1,0) < (0,-1) < (0,1) < (1,0).
  %  - the state SPACE is infinite; the number of states UCS EXPLORES before
  %    the goal is finite. My first justification for (i) mixed those up.
  %  - (iii) could be read loosely as "never explores anything costlier than
  %    the goal", which is true. The justification is written out so the tie
  %    argument is visible.
  \begin{enumerate}
    \item False. The state space is infinite, but UCS processes states in order of past
    cost and every step costs at least 1, so a state with past cost below the goal's cost is within
    that many steps of the origin. There are only finitely many such states, so UCS reaches the goal
    and terminates.

    \item False. UCS returns the minimum-cost path, but it explores outside the rectangle:
    $(-1, 0)$ and $(0, -1)$ each cost 1 to reach, which is cheaper than any goal beyond the origin, so
    they are processed even though they lie outside $0 \le x \le m$, $0 \le y \le n$.

    \item False. UCS does return the minimum-cost path, but it can explore locations whose
    past cost \emph{equals} the minimum rather than being strictly less than it. When several states
    tie for the lowest cost, the queue's tie-break decides the order. For the goal $(1, 0)$, which costs
    1, the states $(-1, 0)$, $(0, -1)$ and $(0, 1)$ also have past cost 1 and are popped before the goal.
  \end{enumerate}
  % ### END CODE HERE ###
\end{answer}

\begin{answer}
  % ### START CODE HERE ###
  % Kept for reference, not rendered. What I had to get straight:
  %  - "arbitrary graph" means ANY graph. A True answer must hold for every
  %    graph; a False answer needs only one counterexample graph.
  %  - (i): I first said False, then "it's whatever the direct connection is".
  %    Wrong: adding A-C at cost 100 does not delete A-B-C at 20, so the minimum
  %    stays 20. The minimum is the cheapest of ALL paths, not the newest edge.
  %    What matters is the cheapest full path using the new edge, not the edge
  %    cost alone.
  %  - (iii): I briefly argued True from a three-edge example that did not
  %    flip. One graph where the path stays the same proves nothing; one graph
  %    where it changes proves False.
  \begin{enumerate}
    \item True. Adding a connection only adds paths and never removes one, so the minimum
    over the larger set of paths cannot exceed the minimum over the smaller set. The distance either
    drops, if the best path through the new connection is cheaper, or stays the same.

    \item False. An action out of a state that the start cannot reach lies on no path from
    the start to the goal, however small its cost. For example, with $A \xrightarrow{5} C$ as the only
    route from start $A$ to goal $C$ and a separate component $D \xrightarrow{-1000} E$, the cheap action
    never appears in the minimum-cost path. The same holds for an action leading into a dead end.

    \item False. Adding 1 to every action raises a path's cost by its number of edges, so paths
    with more edges are penalised more and the ranking can change. Take route 1, $A \xrightarrow{10} Z$
    with one edge, and route 2, $A \xrightarrow{2} B \xrightarrow{2} C \xrightarrow{2} D \xrightarrow{2} Z$
    with four. Before the change route 1 costs 10 and route 2 costs 8, so route 2 is the minimum. After
    adding 1 to every action, route 1 costs 11 and route 2 costs 12, so route 1 becomes the minimum-cost path.
  \end{enumerate}
  % ### END CODE HERE ###
\end{answer}

% <SCPD_SUBMISSION_TAG>_2c
\begin{answer}
  % ### START CODE HERE ###
  If everyone plans with the same system, the users all get sent down the same shortest path, and
  the congestion that creates never shows up in the cost, because the cost is only distance. The
  people who do not use it are hit whenever their own route intersects that optimal path, so quiet
  side streets that were never built for through traffic end up carrying it, and they get none of
  the benefit since they never opted in. The mismatch is that the model prices an edge as a fixed
  number when the real price depends on how many people are on it at the time, and the system has no
  way of knowing that its own advice is what put them there. One way to reduce that is to put actual
  speed into the cost rather than distance alone, so a road that is slow or already saturated costs
  more and the system spreads people out instead of funnelling them all onto one route.
  % ### END CODE HERE ###
\end{answer}

% <SCPD_SUBMISSION_TAG>_3b
\begin{answer}
  % ### START CODE HERE ###
  The maximum number of states UCS could visit is
  \[
    n \cdot 2^{k} .
  \]
  A state is a location together with the set of waypoint tags covered so far, so there are $n$
  choices for the location, and for the memory each of the $k$ tags is independently either covered
  or not, which gives $2^{k}$ possible sets. Multiplying the two independent choices gives
  $n \cdot 2^{k}$.
  % ### END CODE HERE ###
\end{answer}

  home. A route that is optimal in distance can still be the wrong plan for the day.

\begin{answer}
  % ### START CODE HERE ###
  Between a drop-off and the next pick-up I would insert a rest waypoint, tagged for a restroom,
  food, or somewhere to park for ten minutes, in the same way problem 4c joins a fake node to every
  end location at zero cost so the search finds whichever one is nearest. Here the cost would be
  small rather than zero, so a break is cheap enough that the route takes one but not so free that
  the driver is sent miles out of the way for it. To pick sensible waypoints I would want the
  driver's age and years of driving experience, since a new driver and a driver in their seventies
  do not need the same break pattern or the same length of shift. Those same two fields are exactly
  what a company could turn against them: knowing a driver's age lets dispatch quietly stop sending
  work to older drivers, which is age discrimination dressed up as routing, and it never has to be
  written down anywhere because it only shows up as fewer jobs.
  % ### END CODE HERE ###
\end{answer}
