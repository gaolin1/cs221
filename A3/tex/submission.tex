\begin{answer}
  % ### START CODE HERE ###
  % Kept for reference, not rendered. How I got here:
  %  - Cost((x, y), a) is priced on the state being LEFT, and depends only on
  %    x: 1 + x for x >= 0, and 1 for x < 0. Direction does not matter, so a
  %    north step from x = 2 costs 3, not 1.
  %  - each action moves one coordinate by one, so every step is priced
  %    separately; the formula is applied per step, never once per leg
  %  - checked by hand: (2, 1) north-first costs 1 + 1 + 2 = 4, while
  %    east-first costs 1 + 2 + 3 = 6; (3, 0) costs 1 + 2 + 3 = 6
  %  - guesses that failed a hand check: 1 + m, 1 + m + n, 2n + m, 2m + n
  %  - closed form of 1 + 2 + ... + m by writing the series forwards and
  %    backwards: m columns each summing to m + 1, two copies of the series,
  %    so the sum is m(m + 1)/2. Works for odd m, where pairing leaves a middle
  %    term.
  \textbf{Minimum cost.}
  \[
    \frac{m(m+1)}{2} + n .
  \]

  \medskip
  Every step is priced by the $x$ coordinate of the location being left, whatever the direction.
  The $n$ north steps each cost exactly 1 if they are taken while $x = 0$, contributing $n$. The $m$
  east steps have to leave from $x = 0, 1, \dots, m-1$ in turn, costing $1, 2, \dots, m$, which sums
  to $m(m+1)/2$.

  \medskip
  \textbf{Path.} Take all $n$ steps north from the origin first, then all $m$ steps east.

  \medskip
  \textbf{Uniqueness.} The path is unique. Any north step taken after moving east costs more than 1,
  since it leaves from $x > 0$, and a detour into negative $x$ adds at least one step west and one
  step back east, each costing at least 1, without making any other step cheaper.
  % ### END CODE HERE ###
\end{answer}

\begin{answer}
  % ### START CODE HERE ###
  % Kept for reference, not rendered. What I had to get straight:
  %  - "pop" means taking a state OUT of the frontier to process it. Popping a
  %    state makes its cost final; it does not stop the search. UCS stops only
  %    when the state it pops is the goal.
  %  - the frontier is a priority queue deciding who gets processed next,
  %    ordered by past cost. Expanding a state pushes all four neighbours, but
  %    UCS always processes the cheapest known state next, so it grows in rings
  %    of increasing cost rather than racing off in every direction.
  %  - ties are not random here: util.PriorityQueue stores (priority, state)
  %    tuples, so equal priorities are broken by comparing the states, lower x
  %    first then lower y: (-1,0) < (0,-1) < (0,1) < (1,0).
  %  - the state SPACE is infinite; the number of states UCS EXPLORES before
  %    the goal is finite. My first justification for (i) mixed those up.
  %  - (iii) could be read loosely as "never explores anything costlier than
  %    the goal", which is true. The justification is written out so the tie
  %    argument is visible.
  \begin{enumerate}
    \item \textbf{False.} The state space is infinite, but UCS processes states in order of past
    cost and every step costs at least 1, so a state with past cost below the goal's cost is within
    that many steps of the origin. There are only finitely many such states, so UCS reaches the goal
    and terminates.

    \item \textbf{False.} UCS returns the minimum-cost path, but it explores outside the rectangle:
    $(-1, 0)$ and $(0, -1)$ each cost 1 to reach, which is cheaper than any goal beyond the origin, so
    they are processed even though they lie outside $0 \le x \le m$, $0 \le y \le n$.

    \item \textbf{False.} UCS does return the minimum-cost path, but it can explore locations whose
    past cost \emph{equals} the minimum rather than being strictly less than it. When several states
    tie for the lowest cost, the queue's tie-break decides the order. For the goal $(1, 0)$, which costs
    1, the states $(-1, 0)$, $(0, -1)$ and $(0, 1)$ also have past cost 1 and are popped before the goal.
  \end{enumerate}
  % ### END CODE HERE ###
\end{answer}

  % ### START CODE HERE ###
  % Kept for reference, not rendered. What I had to get straight:
  %  - "arbitrary graph" means ANY graph. A True answer must hold for every
  %    graph; a False answer needs only one counterexample graph.
  %  - (i): I first said False, then "it's whatever the direct connection is".
  %    Wrong: adding A-C at cost 100 does not delete A-B-C at 20, so the minimum
  %    stays 20. The minimum is the cheapest of ALL paths, not the newest edge.
  %    What matters is the cheapest full path using the new edge, not the edge
  %    cost alone.
  %  - (iii): I briefly argued True from a three-edge example that did not
  %    flip. One graph where the path stays the same proves nothing; one graph
  %    where it changes proves False.
  \begin{enumerate}
    \item \textbf{True.} Adding a connection only adds paths and never removes one, so the minimum
    over the larger set of paths cannot exceed the minimum over the smaller set. The distance either
    drops, if the best path through the new connection is cheaper, or stays the same.

    \item \textbf{False.} An action out of a state that the start cannot reach lies on no path from
    the start to the goal, however small its cost. For example, with $A \xrightarrow{5} C$ as the only
    route from start $A$ to goal $C$ and a separate component $D \xrightarrow{-1000} E$, the cheap action
    never appears in the minimum-cost path. The same holds for an action leading into a dead end.

    \item \textbf{False.} Adding 1 to every action raises a path's cost by its number of edges, so paths
    with more edges are penalised more and the ranking can change. Take route 1, $A \xrightarrow{10} Z$
    with one edge, and route 2, $A \xrightarrow{2} B \xrightarrow{2} C \xrightarrow{2} D \xrightarrow{2} Z$
    with four. Before the change route 1 costs 10 and route 2 costs 8, so route 2 is the minimum. After
    adding 1 to every action, route 1 costs 11 and route 2 costs 12, so route 1 becomes the minimum-cost path.
  \end{enumerate}
  % ### END CODE HERE ###
\end{answer}
