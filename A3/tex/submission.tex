\begin{answer}

  % Kept for reference, not rendered. How I got here:
  %  - Cost((x, y), a) is priced on the state being LEFT, and depends only on
  %    x: 1 + x for x >= 0, and 1 for x < 0. Direction does not matter, so a
  %    north step from x = 2 costs 3, not 1.
  %  - each action moves one coordinate by one, so every step is priced
  %    separately; the formula is applied per step, never once per leg
  %  - checked by hand: (2, 1) north-first costs 1 + 1 + 2 = 4, while
  %    east-first costs 1 + 2 + 3 = 6; (3, 0) costs 1 + 2 + 3 = 6
  %  - guesses that failed a hand check: 1 + m, 1 + m + n, 2n + m, 2m + n
  %  - closed form of 1 + 2 + ... + m by writing the series forwards and
  %    backwards: m columns each summing to m + 1, two copies of the series,
  %    so the sum is m(m + 1)/2. Works for odd m, where pairing leaves a middle
  %    term.
  The minimum cost of reaching $(m,n)$ from $(0,0)$ is
  \[
    \frac{m(m+1)}{2} + n .
  \]
  The cost only depends on the $x$ being left, so take all $n$ north steps while still at $x = 0$,
  where each costs 1 and they total $n$, then the $m$ east steps leave from $x = 0, 1, \dots, m-1$
  in turn and cost $1, 2, \dots, m$; writing that series forwards and backwards pairs it into $m$
  columns of $m+1$, so it sums to $m(m+1)/2$. One path achieving the minimum is to take all $n$
  steps north from the origin first and then all $m$ steps east, and it is the only one, since any
  north step taken after moving east costs more than 1 because it leaves from $x > 0$, and a detour
  into negative $x$ adds at least one step west and one step back east, each costing at least 1,
  without making any other step cheaper.
  % ### END CODE HERE ###
\end{answer}

  % Kept for reference, not rendered. What I had to get straight:
  %  - "pop" means taking a state OUT of the frontier to process it. Popping a
  %    state makes its cost final; it does not stop the search. UCS stops only
  %    when the state it pops is the goal.
  %  - the frontier is a priority queue deciding who gets processed next,
  %    ordered by past cost. Expanding a state pushes all four neighbours, but
  %    UCS always processes the cheapest known state next, so it grows in rings
  %    of increasing cost rather than racing off in every direction.
  %  - ties are not random here: util.PriorityQueue stores (priority, state)
  %    tuples, so equal priorities are broken by comparing the states, lower x
  %    first then lower y: (-1,0) < (0,-1) < (0,1) < (1,0).
  %  - the state SPACE is infinite; the number of states UCS EXPLORES before
  %    the goal is finite. My first justification for (i) mixed those up.
  %  - (iii) could be read loosely as "never explores anything costlier than
  %    the goal", which is true. The justification is written out so the tie
  %    argument is visible.
  \begin{enumerate}
    \item False. The states go on forever, but UCS takes them in cost order and every step costs at
    least 1, so anything cheaper than the goal is only so many steps out from the origin. There are
    only so many of those, so it gets to the goal and stops.

    \item False. It does give back the minimum cost path, but it looks outside the box on the way.
    $(-1, 0)$ and $(0, -1)$ both cost 1 to get to, which is cheaper than most goals, so they get
    processed even though they sit outside $0 \le x \le m$, $0 \le y \le n$.

    \item False. It returns the minimum cost path, but it can also look at places costing exactly
    the same as the minimum rather than less. When things tie, the queue decides who goes first. For
    the goal $(1, 0)$, which costs 1, the states $(-1, 0)$, $(0, -1)$ and $(0, 1)$ also cost 1 and
    come out before it.
  \end{enumerate}

  \begin{enumerate}
    \item True. Adding a connection only gives you more paths, it never takes one away, so the
    minimum can drop or stay where it is but it cannot go up.

    \item False. An action coming out of a state the start cannot get to is not on any path from
    start to goal, however cheap it is. Say $A \xrightarrow{5} C$ is the only way from start $A$ to
    goal $C$, and $D \xrightarrow{-1000} E$ sits off on its own, then that cheap action never shows
    up. Same if it leads into a dead end.

    \item False. Adding 1 to every action charges a path by how many edges it has, so the longer
    ones get hit harder and the order can flip. Route 1 is $A \xrightarrow{10} Z$ with one edge,
    route 2 is $A \xrightarrow{2} B \xrightarrow{2} C \xrightarrow{2} D \xrightarrow{2} Z$ with
    four. Before, route 1 costs 10 and route 2 costs 8, so route 2 wins. After, route 1 costs 11 and
    route 2 costs 12, so route 1 wins.
  \end{enumerate}

% <SCPD_SUBMISSION_TAG>_2c
\begin{answer}
  % ### START CODE HERE ###
  If everyone plans with the same system, the users all get sent down the same shortest path, and
  the congestion that creates never shows up in the cost, because the cost is only distance. The
  people who do not use it are hit whenever their own route intersects that optimal path, so quiet
  side streets that were never built for through traffic end up carrying it, and they get none of
  the benefit since they never opted in. The mismatch is that the model prices an edge as a fixed
  number when the real price depends on how many people are on it at the time, and the system has no
  way of knowing that its own advice is what put them there. One way to reduce that is to put actual
  speed into the cost rather than distance alone, so a road that is slow or already saturated costs
  more and the system spreads people out instead of funnelling them all onto one route.
  % ### END CODE HERE ###
\end{answer}

\begin{answer}
  % ### START CODE HERE ###
  The maximum number of states UCS could visit is
  \[
    n \cdot 2^{k} .
  \]
  A state is a location together with the set of waypoint tags covered so far, so there are $n$
  choices for the location, and for the memory each of the $k$ tags is independently either covered
  or not, which gives $2^{k}$ possible sets. Multiplying the two independent choices gives
  $n \cdot 2^{k}$.
  % ### END CODE HERE ###
\end{answer}

  food, or somewhere to park for ten minutes, in the same way problem 4c joins a fake node to every

\begin{answer}
  % ### START CODE HERE ###
  Both queries went through the support messenger at support.claude.com.

  \medskip
  Query 1, sent about Claude Code:

  \begin{quote}
  I use Claude Code on a Max plan and I'd like to know whether it can be pointed at a different
  model endpoint. I know Bedrock and Vertex are supported. Is there any supported way to use an
  OpenAI-compatible or OpenRouter endpoint, and if not, is that something on the roadmap? I'm asking
  because I want to compare outputs on the same repo without changing tools.
  \end{quote}

  The reply:

  \begin{quote}
  Claude Code can connect through LLM gateways that expose a supported API format, but we don't
  support routing Claude Code to non-Claude models through any gateway.

  While you can configure Claude Code to use different Claude model endpoints (like Bedrock, Vertex,
  Microsoft Foundry, or through custom \texttt{ANTHROPIC\_BASE\_URL} settings), the gateway
  compatibility is specifically for accessing Claude models, not for switching to other model
  providers like OpenAI or OpenRouter.

  For comparing outputs on the same repo, you'd need to use separate tools for non-Claude models. We
  don't have information about future roadmap plans for multi-model support in Claude Code.
  \end{quote}

  \medskip
  Query 2, sent about Claude itself:

  \begin{quote}
  I'm using Claude to learn the maths for a machine learning course, and I want it to tutor me
  rather than solve things for me. The problem I keep hitting is that when I'm deriving something,
  Claude already knows the final form and reasons backwards toward it, which looks like a derivation
  but doesn't help, because the answer is the one thing I don't have. Telling it to stop works for a
  few messages and then it drifts back. Where is the best place to put an instruction like that so
  it holds for a whole session, Project instructions, a custom style, or something else? And is
  there a recommended way to phrase it?
  \end{quote}

  The reply:

  \begin{quote}
  For persistent tutoring instructions, Project instructions are your best option. They apply to all
  chats within that project, so you can keep your ML course work in one project with the tutoring
  behavior locked in.

  Here's how to phrase it effectively. In your project instructions, try something like: ``Act as a
  tutor, not a solver. When I'm deriving equations or working through problems, guide me with hints
  and questions rather than showing the final form or working backwards from the answer. Let me
  discover the solution step-by-step. If I get stuck, ask what I've tried or suggest the next small
  step, but don't reveal the destination.''

  You could also add this to your account-wide Instructions for Claude (Settings $\rightarrow$
  Instructions for Claude) if you want this tutoring approach across all your conversations, not
  just in one project. Project instructions work on top of your account instructions, so you can
  combine both, general preferences account-wide and specific tutoring rules in your ML project.
  \end{quote}

  Both queries were returned through the online fin agent without human replies.
  % ### END CODE HERE ###
\end{answer}
